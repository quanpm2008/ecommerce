# identity-service — Progress

The "Identity & Seller" service. It owns `User`, `Customer`, `Seller`, `CustomerAddress`, `Role`, `Permission`, `UserRole` and `RolePermission`. It issues JWTs and provides the authorization context that other services call (see `docs/api.docx` §3.2, §6.1 and `docs/database.docx` §3.1).

## Done

- **Scaffold**: Spring Boot 4.1.2, Java 21, Spring Cloud, package `com.example.identity_service`. `IdentityServiceApplication` is annotated with `@EnableDiscoveryClient`.
- **Dependencies** (`pom.xml`):
  - `spring-boot-starter-webmvc`
  - `spring-boot-starter-actuator`
  - `spring-cloud-starter-netflix-eureka-client`
  - `spring-cloud-starter-openfeign`
  - the `postgresql` driver
  - `spring-boot-starter-data-jpa`, `spring-boot-starter-flyway` + `flyway-database-postgresql`, `spring-boot-starter-validation`
  - `software.amazon.awssdk:s3` (BOM 2.49.0) for presigned media URLs on S3-compatible storage
  - `spring-boot-starter-security` + `spring-boot-starter-security-oauth2-resource-server` (JWT signing with Nimbus, Bearer token checks, password hashing); test: `spring-boot-starter-security-test`
  - `lombok` (optional, compile-time only; run through the compiler's annotation processor and excluded from the jar)
  - test: `spring-boot-starter-data-jpa-test`, `spring-boot-starter-webmvc-test`, `spring-boot-testcontainers`, `testcontainers-postgresql`, `testcontainers-junit-jupiter`
- **Config** (`application.properties`):
  - `spring.application.name=identity-service`, `server.port=8083`, Eureka at `http://localhost:8761/eureka/`
  - default datasource `jdbc:postgresql://localhost:5432/ecommerce` for running on the host (overridden by `SPRING_DATASOURCE_*` in Docker)
  - all tables live in the PostgreSQL schema **`identity`**: Flyway creates it and keeps `identity.flyway_schema_history` there; Hibernate uses it as the default schema, and `spring.datasource.hikari.schema=identity` sets the search path on every pooled connection so `JdbcTemplate` and native SQL resolve unqualified table names there too
  - `ddl-auto=validate` (schema changes only through Flyway), `open-in-view=false`
  - paging: 1-based `page`, default `size` 20, max 100
  - tokens: `identity.token.issuer=ecommerce-identity`, `audience=ecommerce-api`, `access-ttl=PT15M`, `refresh-ttl=P7D` (P-06 proposal), `signing-key` (PKCS#8 PEM RSA private key, env `IDENTITY_TOKEN_SIGNING_KEY`; blank → temporary key, dev only)
  - log lines include `[requestId]`
- **Migrations**: Flyway, SQL files in `src/main/resources/db/migration` (`V<n>__<description>.sql`). Never edit an applied migration; add a new one.
  - `V1__identity_schema.sql`: every Identity table from DB §3.1 and §6 — `users`, `customers`, `sellers`, `customer_addresses`, `roles`, `permissions`, `user_roles`, `role_permissions`, `auth_sessions`, `password_reset_tokens`, `admin_audit_log`, `outbox_events`. No `LoginIdentifier` or `AdminAccount` table.
  - Enums are `VARCHAR` + `CHECK` (mapped with `@Enumerated(STRING)`). Conditional fields are biconditional CHECKs: e.g. `disabled_reason` is set exactly when DISABLED, `rejection_reason` exactly when REJECTED, `reviewed_at`/`reviewed_by_user_id` exactly when not PENDING. Clear them when the state goes back.
  - The database also enforces: email stored trimmed + lowercase, phone numbers in `0xxxxxxxxx` form (`users`, `sellers.contact_phone`, `customer_addresses.recipient_phone`), the LOCAL/GOOGLE credential split, no self-review of a seller application.
  - `seller_name` (normalized: trimmed, whitespace collapsed, lowercase) and `contact_phone` are unique through partial indexes over PENDING/APPROVED sellers, so a REJECTED seller frees them.
  - `customers.ban_mode` + `has_paid_order_before_ban` hold the G-14 policy snapshot taken at ban time (API §10.4); required exactly when BANNED.
  - `customer_addresses.deleted_at` is the soft delete (G-13). The default address is derived, not stored.
  - `V2__seed_rbac.sql`: roles CUSTOMER/SELLER/ADMIN and the API §3.2.1 permission matrix (9/7/7). The three baseline permissions are in `permissions` but linked to no role.
  - `V3__rotated_refresh_tokens.sql`: hashes of refresh tokens already rotated away from a session, for reuse detection.
- **Domain model** (entities validated by `ddl-auto=validate`): `user.User` (+ `UserRepository`), `customer.Customer` / `CustomerAddress`, `seller.Seller` (profiles use `@MapsId`, so their id *is* the user id), `rbac.Role` / `Permission` / `UserRole`, `audit.AdminAuditLog` (`before_after` is JSONB). Entities use Lombok `@Getter` + `@NoArgsConstructor(access = PROTECTED)` and a creation constructor; there are no setters, and state changes go through methods added with the features that need them. Never put `@Data`, `@Setter`, `@EqualsAndHashCode` or `@ToString` on an entity (they bypass invariants such as the `authzVersion` bump, break Hibernate identity, and `toString` would load lazy associations and print `passwordHash`). Services use `@RequiredArgsConstructor` and `@Slf4j`. `User.disable(reason)` / `enable()` bump `authzVersion`. `password_reset_tokens` and `outbox_events` have no entity yet (steps 3, 9).
- **Role changes** (`rbac.RoleAssignments`): the only way to grant or revoke a role. An effective change bumps `authzVersion` in the same transaction (re-granting reuses the revoked row); a no-op returns `false` without a bump. Callers write the audit row and event.
- **Effective permissions** (`rbac.PermissionResolver`): baseline policy (`rbac.Permissions.BASELINE`) + the union of unrevoked roles, read from the database on every call; a DISABLED user has none. Profile status and ownership are not part of it; endpoints check them.
- **Password policy** (`user.PasswordPolicy`): G-07 (≥ 8 chars, upper, lower, digit) plus BCrypt's 72-byte limit. Hashes use Spring's delegating encoder (`{bcrypt}...`, bean in `common.security.PasswordConfig`).
- **Tokens and sessions** (`session` package, API §3.2):
  - Access tokens are RS256 JWTs with exactly `sub`, `iss`, `aud`, `iat`, `exp`, `jti`, `sessionId`, `authzVersion` (`AccessTokenIssuer`); no email, phone, roles or permissions. The key id is the JWK thumbprint (`SigningKeyConfig`).
  - `GET /.well-known/jwks.json` (`JwksController`) publishes the public key in plain JWKS format (not the `data` envelope) for the gateway and other services; it isn't under `/api/v1`, so the gateway doesn't route it.
  - `SessionService`: `start(user)` creates an `AuthSession` (one per login) and returns `IssuedTokens`; `refresh(token)` rotates the refresh token (sliding `expires_at`), keeps the old hash in `rotated_refresh_tokens`, and revokes the whole session if a rotated token comes back. Unknown, expired, revoked or reused tokens and disabled users → `INVALID_REFRESH_TOKEN`. `revoke(sessionId)` and `revokeAllOf(userId)` for logout, password changes and disable. Refresh tokens are 256 random bits; only their SHA-256 hash is stored.
  - New access tokens always carry the user's current `authzVersion`, read from the database.
- **Security** (`common.security.SecurityConfig`): stateless Bearer resource server, no CSRF or HTTP session. Public: `/actuator/health`, `/hello`, the JWKS path; everything else needs a token (step 3 opens the auth endpoints). Each request is checked by `AccessTokenDecoderConfig`: RS256 only, `exp` (60 s skew), `iss`, `aud`, then `SessionTokenValidator` (session exists, belongs to `sub`, not revoked; user ACTIVE; `authzVersion` current), with no caching. `SecurityErrorHandler` writes 401/403 in the error envelope: `TOKEN_EXPIRED`, `TOKEN_STALE`, otherwise `UNAUTHENTICATED`; 403 → `FORBIDDEN`. Times come from a `Clock` bean (`common.time.ClockConfig`).
- **Paths**: controllers serve the full public path (`/api/v1/identity/...`); internal endpoints will use `/internal/v1/identity/...`. The gateway forwards paths unchanged.
- **Auth endpoints** (`auth.AuthController` → `AuthService`, `PasswordService`; API §6.1):
  - `POST /auth/register`: User LOCAL + Customer + CUSTOMER role in one transaction → 201 `UserSelfProfile`, no tokens. `POST /auth/register-seller`: User LOCAL (no personal phone) + Seller PENDING, no role, plus a `seller.registered` outbox event. Email is lowercased, phones normalized (`user.PhoneNumbers`), `confirmPassword` must match, G-07 → `PASSWORD_POLICY_VIOLATION`; duplicates → 409 `EMAIL_ALREADY_USED` / `PHONE_ALREADY_USED` / `SELLER_NAME_ALREADY_USED` with the field in `details` (pre-checked, and a racing unique-index violation is translated by `UniqueConflicts`).
  - `POST /auth/login`: one login for every role → `AuthTokens` (`accessToken`, `accessTokenExpiresIn`, `tokenType`, `refreshToken`, `profile`). Unknown email and wrong password give the same `INVALID_CREDENTIALS` (a dummy BCrypt check evens out timing); Google accounts → 409 `WRONG_AUTH_METHOD` with `details[0].authMethod`; DISABLED → 403 `ACCOUNT_DISABLED`, but only after the password matched. PENDING/REJECTED/BANNED profiles still log in.
  - `POST /auth/refresh` → `AuthTokens` with the profile rebuilt from the database. `POST /auth/logout` (needs the access token) revokes the session only if the refresh token (current or rotated) belongs to the caller's own session; anything else → 204 and no change.
  - `POST /auth/password/forgot` → always the same 202 (G-05); only an ACTIVE LOCAL user gets a 30-minute (P-05) single-use token, stored as a hash, and a `password.reset_requested` outbox event whose `resetUrl` is `identity.password-reset.link-base?token=...`. `POST /auth/password/reset` → 204, sets the password, revokes every session; `RESET_TOKEN_INVALID` for unknown/used/expired links. `PUT /users/me/password` (`account:update:own`, LOCAL only, Google → 403) checks `PASSWORD_INCORRECT` / `PASSWORD_SAME_AS_OLD` and revokes every session including the current one.
  - Rate limits per client IP (`common.web.RateLimiter`, in memory, fixed window): register + register-seller share 10/hour, forgot 5/15 min (`identity.rate-limit.*`; N-04 gives no numbers). The IP is `request.getRemoteAddr()` with `server.forward-headers-strategy=native`, so `X-Forwarded-For` counts only from internal addresses (the gateway).
- **Self-service** (`account` package, API §6.1, UC-A01, A02, A06):
  - `GET /users/me` (`account:read:own`) → `UserSelfProfile`. `PATCH /users/me` (`account:update:own`) accepts only `fullName` and `phoneNumber` (normalized, unique → 409); any other field → 400 `VALIDATION_ERROR` with `issue: UNKNOWN_FIELD` (`common.web.StrictBody`, also used by the seller endpoints).
  - `POST /users/me/customer-profile` (any authenticated user, baseline policy): 201 creates Customer + CUSTOMER (bumps `authzVersion`, so older tokens get `TOKEN_STALE`); 200 if it exists, even BANNED (returned unchanged); 403 if an admin revoked CUSTOMER.
  - `POST /users/me/seller-application` (`seller:application:own`): 201 first time, 200 resubmission after REJECTED (same `seller_id`, review fields cleared), 409 `INVALID_STATE_TRANSITION` with `currentStatus` when PENDING/APPROVED; body only `sellerName`, `contactPhone`, `description`. Writes `seller.registered`. `GET` returns the own `SellerSelfProfile` or `null`.
  - `PATCH /sellers/me` (`seller:profile:own`, APPROVED + ACTIVE seller only, else 403): `description`, `contactPhone`, `logoObjectKey`; never name or email.
- **Media** (`media` package, API §3.9): S3-compatible storage (SeaweedFS in compose) via the AWS SDK. `POST /media/upload-urls` (`seller:profile:own`, operating seller) takes one `SELLER_LOGO` file (JPG/PNG/WebP ≤ 2 MB, P-08) and returns `{ objectKey, uploadUrl, expiresAt }`: a 10-minute presigned PUT bound to the declared type and size, key `seller-logos/<sellerId>/<uuid>.<ext>`. `PATCH /sellers/me` then checks the key prefix (owner), that the object exists, its size and its magic bytes (`SellerLogos`) → 422 `MEDIA_INVALID` otherwise. `logoUrl` in profiles is a 1-hour presigned GET. Presigned URLs are signed for `identity.media.public-endpoint` (the browser's view), while the service itself uses `identity.media.endpoint`. The bucket is created on first use; storage failures → 503 `SERVICE_UNAVAILABLE`.
- **Addresses** (`customer.AddressController`, `customer:profile:own`, DB §3.1.4): list/create/update/delete scoped to `customerId = sub` (another customer's id → 404). Ordered latest `lastUsedAt` first, then never-used ones by `createdAt`; the first is `isDefault`; `meta.maxAddresses` = 5 (P-09, `identity.address.max-per-customer`) → 422 `ADDRESS_LIMIT_EXCEEDED`. The ward is checked against the province through `region.RegionCatalog` → 422 `INVALID_REGION`, or 503 `REGION_SOURCE_UNAVAILABLE` if the source can't answer; names come from the same source and are null when it's down. Delete is hard for never-used addresses and soft (`deleted_at`) once used by a checkout. Writes lock the Customer row; a BANNED customer can read but not change the book; a user without Customer profile → 403.
- **Regions** (`region` package, API §6.1 "Nguồn dữ liệu địa giới"): public `GET /regions/provinces` and `GET /regions/provinces/{provinceCode}/wards` return `[{ code, name }]` / `[{ code, name, provinceCode }]` with `meta { sourceVersion, fetchedAt }`. `OpenApiVnRegionProvider` calls `identity.region.base-url` (`GEO_API_BASE_URL`, default `https://provinces.open-api.vn/api/v2`: `GET /p/`, `GET /p/{code}?depth=2`) with a 3 s timeout, and maps its integer codes to the official zero-padded strings (`01`, `00004`). `RegionCatalog` caches each list for 24 h (`identity.region.cache-ttl`) and serves it only while valid; an expired entry with the source down, a blank base URL, a timeout or a 5xx → 503 `REGION_SOURCE_UNAVAILABLE`, never a static list. `INVALID_REGION` (422) only when the source's own data says no: a province missing from its list (or its 404), or a ward not in that province's wards. `sourceVersion` is the configured `identity.region.dataset-version` because the provider publishes no version.
- **Profiles** (`account.SelfProfileAssembler`): `UserSelfProfile` with current roles and permissions, `CustomerProfile` (`paymentBlocked`, `accessMode` FULL / PAYMENT_BLOCKED / BLOCKED from the G-14 ban mode, `profileComplete` = phone + at least one address) and `SellerSelfProfile` (`logoUrl` as a presigned GET).
- **Permission checks**: `common.security.PermissionAuthentication` turns the caller's current permissions (database, never the token) into Spring authorities, so endpoints use `@PreAuthorize("hasAuthority('...')")` (method security is on). Denials inside MVC → 403 `FORBIDDEN` via `GlobalExceptionHandler`. `common.security.Caller.of(jwt)` gives the caller's `userId` and `sessionId`.
- **Outbox** (`outbox.OutboxWriter`): writes the API §7.2 envelope (`eventId`, `eventType`, `occurredAt`, `producer`, `aggregateId`, `actor`, `payload`) into `outbox_events.payload` in the caller's transaction (`Propagation.MANDATORY`). Nothing publishes it yet (step 9).
- **Admin bootstrap** (`bootstrap.AdminBootstrap`): if `identity.bootstrap.admin.email` is set, startup creates that User (LOCAL, ACTIVE) with the ADMIN role and an audit row (`GRANT_ROLE`, actor null). Password from `identity.bootstrap.admin.password` must pass the policy or startup fails; `full-name` defaults to `Administrator`. ADMIN is granted through `RoleAssignments`, so the new admin is at `authzVersion` 2. If the email already belongs to a user, nothing happens: an existing account is never escalated. In Docker or on the host, use `IDENTITY_BOOTSTRAP_ADMIN_EMAIL` / `IDENTITY_BOOTSTRAP_ADMIN_PASSWORD`.
- **Response envelope** (`common.web.ApiResponse`): controllers return `ApiResponse.of(dto)` → `{ "data": ... }` or `ApiResponse.page(page)` → `{ "data": [...], "meta": { page, size, totalItems, totalPages } }` (`PageMeta` converts to 1-based).
- **Errors** (`common.error`):
  - `ErrorCode` enum holds API §4.1 codes with their HTTP status and default English message (the spec asks for Vietnamese; English was chosen for this service). Only the generic codes exist so far; add feature codes when implementing them.
  - Throw `ApiException(code[, message, details])` from application code.
  - `GlobalExceptionHandler` renders every MVC exception as `{ "error": { code, message, details, requestId } }`. Bean validation → 400 `VALIDATION_ERROR` with `details: [{ field, issue, message }]` (`issue` is the constraint in UPPER_SNAKE, e.g. `NOT_BLANK`). Spring's own errors keep their status: 404 → `NOT_FOUND`, other 4xx (malformed JSON, 405, 415, ...) → `VALIDATION_ERROR`, 5xx → `INTERNAL_ERROR`. Unexpected exceptions are logged and return a generic message.
- **Request id** (`common.web.RequestIdFilter`): the gateway generates `X-Request-Id`; this service never invents one. An incoming value matching `[A-Za-z0-9._-]{1,128}` is echoed on the response and put in the log MDC and `error.requestId`. A missing or unsafe value is ignored: no response header, no id in logs, `error.requestId: null`.
- **Docker**:
  - Two-stage Dockerfile: Maven build, then `eclipse-temurin:21-jre`, running as UID 10001 and exposing 8083.
  - `.dockerignore`.
- **Compose**:
  - Registered via the `x-eureka-client` anchor, published on port 8083.
  - Waits for `discovery-service` and `database` to be healthy.
  - Gets `SPRING_DATASOURCE_URL=jdbc:postgresql://database:5432/ecommerce` (user and password `ecommerce`). This dev database is shared by all services.
- **Tests**: `mvn test` starts a throwaway `postgres:16` with Testcontainers (`TestcontainersConfiguration`, import it with `@Import`); Docker must be running. `IdentityServiceApplicationTests` checks the context, the applied migration versions and the exact table list of the `identity` schema; `SchemaConstraintsTests` checks the DB rules above with plain SQL (one expected violation per test, since a failed statement aborts the PostgreSQL transaction); `rbac.RbacSeedTests` compares the seed with the spec matrix (`rbac.RbacMatrix`, written out independently); `rbac.PermissionResolverTests`, `rbac.RoleAssignmentsTests` and `bootstrap.AdminBootstrapTests` cover effective permissions, role changes and the bootstrap; `session.SessionServiceTests` (claims, lifetimes, hashing, rotation, reuse, rejections), `session.AccessTokenAuthenticationTests` (the real filter chain: valid, missing, expired, stale, revoked, disabled, foreign key, `alg: none`, wrong `iss`/`aud`, swapped `sessionId`, JWKS) and `session.SigningKeyConfigTests` cover tokens. `auth.AuthEndpointsTests` and `auth.PasswordEndpointsTests` (sharing `AuthEndpointTestSupport`: one context, unique emails/phones and a random client IP per test) cover the auth endpoints; `auth.UniqueConflictsTests`, `user.PhoneNumbersTests` and `common.web.RateLimiterTests` are plain unit tests. Step 4: `account.AccountEndpointsTests`, `account.SellerAccountEndpointsTests` (real presigned PUT/GET against SeaweedFS), `customer.AddressEndpointsTests`, plus `media.SellerLogosTests` and `common.web.StrictBodyTests`. Step 5: `region.RegionEndpointsTests` (cache, outage, unknown province) and `region.OpenApiVnRegionProviderTests` (the HTTP adapter against a local `HttpServer` standing in for the upstream: code mapping, 404, 5xx, timeout, unconfigured). All endpoint tests extend `EndpointTestSupport` (root test package), whose context adds `SeaweedfsTestConfiguration` (container `chrislusf/seaweedfs:4.45`) and `FakeRegionProvider` (a small dataset with an outage switch). `MutableClock` is truncated to microseconds like PostgreSQL, which fixed a flaky reset-expiry test. Time-dependent tests use `MutableClock` via `TestClockConfiguration`; `common.WebContractTests` is a `@WebMvcTest` slice (no database, no Docker) covering the envelope, paging, error mapping and request id through a test-only controller. Open improvements from Codex reviews (step 0 tests, audit package) are listed in [should.md](should.md).

## Notes / open issues

- Token lifetimes (15 min access / 7 days refresh, P-06) are not finalized in the spec.
- Paging is lenient: `page` ≤ 0 is treated as page 1 and `size` > 100 is capped at 100, instead of returning 400. Revisit if the FE needs strict validation.
- Every effective role change bumps `authzVersion`, even the first grant of a brand-new user (decided in step 2 for one simple rule; registration will leave a new customer at version 2).
- Two refreshes racing with the same token: the second sees a rotated token and revokes the session, so the client must log in again. Strict on purpose (no grace period); revisit if the FE refreshes from several tabs at once.
- The refresh token's expiry slides on every rotation (7 days from the last refresh), so an active session never expires. The spec only says "7 days"; add an absolute session limit if needed.
- `iss`/`aud` values (`ecommerce-identity` / `ecommerce-api`) are our choice, not the spec's; the gateway and every service must verify the same values and fetch keys from `http://identity-service:8083/.well-known/jwks.json` (Docker) or `http://localhost:8083/...` (host).
- The API's register example shows `authzVersion: 1`; ours is 2 because granting CUSTOMER bumps it (step 2 rule). Harmless, but FE should not assume 1.
- Google sign-in (`POST /auth/google`, Should) is not built: it needs a Google OAuth client id and verification against Google's keys.
- Rate limits live in memory per instance and reset on restart; login has no brute-force limit yet (not in the checklist). The gateway is expected to add shared limits.
- The `password.reset_requested` outbox row holds the raw reset URL (Notification needs it), so the token exists unhashed in `outbox_events` until published. The step 9 publisher must clear or delete such payloads after delivery.
- Older reset links stay valid until they expire when a new one is requested; reset also works for a user disabled after the link was sent (they still cannot log in).
- Outbox envelopes have no per-aggregate `version` yet (API §7.2); decide what it counts in step 9.
- MinIO was the first choice for storage, but its images are no longer pullable (Docker Hub repo gone, quay.io 401); SeaweedFS 4.45 is used instead. Any S3-compatible store works by changing `identity.media.*`.
- Uploaded files that are never attached, and logos replaced later, stay in the bucket: the 24-hour cleanup (N-08) needs a lifecycle rule or job. Browser uploads also need CORS on the storage for the FE origins; not configured yet.
- "Address referenced by an order" is approximated by "used by a checkout" (`last_used_at` set, updated by the step 8 touch endpoint): Identity cannot see Order's data.
- Our choices where the spec is silent: a BANNED customer cannot change the address book; `seller.registered` is also written when an existing user applies or resubmits, not only on `register-seller`.
- No signing key is configured in compose yet, so the Docker identity-service uses a temporary key: tokens die on every restart.
- Outbox has only `PENDING`/`PUBLISHED`; retry counters or a `FAILED` state can be added with the publisher in step 9 (no message broker in the stack yet).
- The region provider is not chosen by the spec ("the team picks one"); provinces.open-api.vn v2 is the default because it serves the current two-level dataset (34 provinces) without credentials. It is a free community service with no SLA or published version: confirm it with the team, or point `GEO_API_BASE_URL` elsewhere (another provider needs its own `RegionProvider` adapter). Identity in Docker needs outbound internet for it.
- The region cache is per instance and in memory, so a restart refetches; with the source down after a restart, address writes are 503 until it returns.
- On this machine (rootless Docker), Testcontainers once failed with "bind: address already in use" on host port 32768; rerunning worked.
